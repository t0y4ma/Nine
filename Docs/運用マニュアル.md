## 1. プロジェクト概要

「Nine」は、1〜9の数字カードを使った対戦型カードゲームです。

- 各プレイヤーは9枚（部屋ごとの設定で変更可能）の数字カードを持つ
- 毎ラウンド、全員が同時にカードを1枚出す
- 一番大きい数字を出した人がそのラウンドの勝者（同点は無効）
- 全ラウンド終了時、最も多くラウンドに勝った人が総合優勝

### 技術スタック

| 項目 | 内容 |
|---|---|
| ゲームエンジン | Unity 6 (6000.3.10f1) |
| ネットワーク | Mirror + SimpleWebTransport |
| クライアント配信 | WebGL → Cloudflare Pages |
| サーバー | Linux Dedicated Server (IL2CPP) → GCP VM (e2-micro) |
| リバースプロキシ | Caddy（TLS終端、wss://対応） |
| DNS | Dynu (`nine.freeddns.org`) |

### 接続の流れ

```
ブラウザ (WebGLクライアント)
   ↓ wss://nine.freeddns.org:443
Caddy (GCP VM上、TLS終端)
   ↓ ws://127.0.0.1:27777
Linux Dedicated Server (systemdで常時稼働)
```

## 3. フォルダ構成と主要スクリプト

```
Assets/
├── Scenes/
│   └── Game.unity          # メインシーン（ロビー〜ゲーム画面すべてを含む単一シーン）
├── Scripts/
│   ├── Game/
│   │   ├── GameManager.cs      # ラウンド進行・勝敗判定・得点計算（サーバー権威）
│   │   ├── Player.cs           # プレイヤー個別の状態（手札・Ready状態など）
│   │   ├── Room.cs             # 部屋の管理（ホスト権限・参加者リスト）
│   │   ├── RoomManager.cs      # 部屋の作成/参加/ゲーム開始のCommand群
│   │   ├── myNetworkManager.cs # NetworkManager拡張。常時アクティブ（接続前の処理が必要なため）
│   │   └── UIEventsManager.cs  # UI全般のイベント処理・動的レイアウト計算
│   └── UI/
│       ├── ResponsiveCanvasScaler.cs  # 解像度非依存のレスポンシブUIの中核
│       └── NumberCardUI.cs            # 数字カード1枚分の見た目
├── Prefabs/UI/NumberCard.prefab
└── UI/  (RoundedRect.png, RoundedRectSmall.png, WhitePixel.png など9-sliceスプライト)

Versions/
├── WebGL/           # WebGLビルド出力（Cloudflare Pagesにデプロイされる実体）
└── LinuxServer/      # Linuxサーバービルド出力（実行ファイル名は LinuxServer.x86_64 に固定。GCP VMにアップロードする実体）
```

### 各スクリプトの責務（重要）

- **GameManager.cs**: ラウンド進行、タイマー管理、得点計算はすべてここ（`[Server]`属性のメソッドのみが実行権限を持つ）。カード枚数（`CARDCOUNT`）と得点方式（`ScoringMode`）はSyncVarとして同期される。
- **UIEventsManager.cs**: 「Manager」というGameObjectにアタッチされている。**このGameObjectは接続前は非アクティブ**（後述の重要な注意点を参照）。
- **ResponsiveCanvasScaler.cs**: 「Canvas」にアタッチ。**常時アクティブ**。全解像度対応のレイアウト計算をすべて担当する。

## 4. ゲームの基本ルール

- カード枚数: デフォルト9枚（部屋ごとの設定画面で3〜20枚に変更可能）
- 参加人数上限: デフォルト8人（部屋ごとの設定画面で2〜20人に変更可能）
- 得点方式:
  - **モード0（デフォルト）**: ラウンド勝利で1pt
  - **モード1**: ラウンド勝利時、相手（自分以外）が出したカードの数字の合計をpt獲得
- 制限時間: 1ラウンド45秒。全員が選択済みになると残り3秒に短縮。時間切れで未選択のプレイヤーは、未使用カードからランダムに1枚自動選択される。
- ラウンド間の遷移: 最大2.5秒の緩衝時間。全員が「Next」を押せば早く進む。
- 設定（カード枚数・得点方式・参加人数上限）は**部屋ごとに完全に独立**しており、ホストのみ・ゲーム開始前のみ変更可能。

## 5. ローカルでの動作確認方法

### 5.1 基本的な流れ

1. Unity Editorで `Assets/Scenes/Game.unity` を開く
2. Play Modeに入る
3. 「Create Room」でルーム作成 → 自動的にホスト（サーバー兼クライアント）になる
4. 「Join Room」で自分自身も参加
5. 画面下部の「Debug」パネルの「Add Bot」でボット（テスト用の2人目以降のプレイヤー）を追加
6. 双方Readyにして「Start Game」

### 5.2 複数解像度でのテスト

Game ViewのCustom Sizeに、以下の主要解像度を登録して確認する運用にしています（物理ピクセル基準、詳細は9章）:

| 名称 | 解像度 | 用途 |
|---|---|---|
| iPhone 16e | 1170×2532 | スマホ縦の代表 |
| iPad Air M3 | 1640×2360 | タブレット縦の代表 |
| デスクトップ | 1920×1080 | PC横の代表 |
| PC縦長ウィンドウ | 900×1400 | PCでウィンドウを縦長にリサイズしたケース |

**重要**: Game ViewでCustom Sizeを切り替えたら、**必ずPlay Modeを一度停止してから再度Playする**こと。Play Mode中に解像度を切り替えると、CanvasScalerの計算が正しく反映されないことがあります。

### 5.3 UI同士の重なりを機械的にチェックする方法

目視だけでなく、以下のようなコードをUnity内で実行することで、UI要素同士の矩形重なりを客観的に検出できます（このプロジェクトの開発で繰り返し使ったテクニックです）。

```csharp
// Canvasの直接の子要素(+その子要素の実際の描画範囲)を取得し、
// ペアごとに重なりがないかチェックする
var canvas = GameObject.Find("Canvas");
var items = new System.Collections.Generic.List<(string name, Rect rect)>();
for (int i = 0; i < canvas.transform.childCount; i++)
{
    var child = canvas.transform.GetChild(i);
    if (!child.gameObject.activeInHierarchy) continue;
    var rt = child.GetComponent<RectTransform>();
    Vector3[] corners = new Vector3[4];
    rt.GetWorldCorners(corners);
    float minX = corners[0].x, minY = corners[0].y, maxX = corners[2].x, maxY = corners[2].y;
    for (int c = 0; c < child.childCount; c++)
    {
        var gc = child.GetChild(c);
        if (!gc.gameObject.activeInHierarchy) continue;
        var gcRt = gc.GetComponent<RectTransform>();
        if (gcRt == null) continue;
        Vector3[] cc = new Vector3[4];
        gcRt.GetWorldCorners(cc);
        minX = Mathf.Min(minX, cc[0].x); minY = Mathf.Min(minY, cc[0].y);
        maxX = Mathf.Max(maxX, cc[2].x); maxY = Mathf.Max(maxY, cc[2].y);
    }
    items.Add((child.name, new Rect(minX, minY, maxX - minX, maxY - minY)));
}
// items同士のRect.Overlaps()で総当たりチェックする
```

## 6. ビルド手順

### 6.1 WebGLビルド

1. `File > Build Settings` → WebGLを選択
2. **必ず `Development Build` のチェックを外す**（チェックが入っていると `.unityweb` 圧縮ファイルではなく非圧縮の `.wasm`/`.js` が出力され、ファイルサイズが大きくなる）
3. ビルド出力先: `Versions/WebGL/`
4. ビルドは非同期（`manage_build` 経由でビルドした場合は `job_id` をポーリングして完了を待つ）

### 6.2 Linux Dedicated Serverビルド

**前提条件**: Unity Hubで「Linux Dedicated Server Build Support」モジュールがインストール済みであること。入っていないと、`subtarget: server` を指定してもサイレントにPlayerモードのビルドにフォールバックしてしまいます。

1. Scripting Backend: **IL2CPP** を指定（Monoは Unity 6のLinuxサーバーでセグフォルトする既知の問題があるため必須）
2. ビルド出力先: **`Versions/LinuxServer/LinuxServer`に固定**(実行ファイル名が`LinuxServer.x86_64`になるようにする。7.2.1参照。この名前を変えるとサーバー側のsystemd設定も直す必要が出るため、絶対に変えないこと)
3. 出力される主なファイル: `LinuxServer.x86_64`, `GameAssembly.so`, `UnityPlayer.so`, `libdecor-*.so`

### 6.3 Push前のチェックリスト

1. WebGLビルド（`development: false`）→ `.unityweb` ファイルが生成されていることを確認
2. スクリプト + `Versions/WebGL/` + シーンファイルをステージング
3. 以下は除外する: `Versions/Windows/`, `Assets/Screenshots/`, `Assets/Resources.meta`
4. わかりやすいコミットメッセージをつける（**注意**: 過去のコミット履歴に `commit` とだけ書かれたものが複数あります。今後は内容が分かるメッセージを推奨します）
5. **`GameManager`等のSyncVar/Command/RPCに変更がある場合は、Linuxサーバーも同じタイミングで再ビルド・再デプロイする**(7.5参照。これを怠ると原因不明のバグにつながる)
6. `git push origin main`

## 7. デプロイ手順

### 7.1 WebGLクライアント（Cloudflare Pages）

GitHubへのpushをトリガーに、Cloudflare Pagesが自動でデプロイします（静的ホスティング）。手動の追加作業は不要です。

- 公開URL: `https://nine-mja.pages.dev`

### 7.2 サーバー（GCP VM）

**実行ファイル名は `LinuxServer.x86_64` に固定**している（7.2.1参照）。ビルド出力先は必ず `Versions/LinuxServer/LinuxServer` にすること。これにより、以後は名前を気にせず同じ手順を繰り返すだけでよい。

#### GCPブラウザSSHでの具体的な手順

1. Linux Dedicated Serverを再ビルド（出力先: `Versions/LinuxServer/LinuxServer`）
2. PowerShellの `Compress-Archive` でZip化（例: `Versions/LinuxServer_deploy.zip`）
3. https://console.cloud.google.com/compute/instances → 該当インスタンスの「SSH」ボタンでブラウザ内ターミナルを開く
4. 右上の歯車アイコン →「ファイルをアップロード」で `LinuxServer_deploy.zip` をアップロード（ホームディレクトリ `~` に置かれる）
5. ターミナルで以下を実行:
   ```bash
   sudo systemctl stop nine-server
   unzip -o ~/LinuxServer_deploy.zip -d ~/game2
   chmod -R +rX ~/game2
   chmod +x ~/game2/LinuxServer.x86_64
   sudo systemctl start nine-server
   sudo systemctl status nine-server   # active (running) になっていれば成功
   ```
6. ログを見たい場合: `sudo journalctl -u nine-server -f`

### 7.2.1 【重要】実行ファイル名を固定する（初回のみのセットアップ）

ビルドのたびにUnityが出力するファイル名が変わってしまうと、systemdサービス側のパスも毎回確認・修正する必要があり非常に手間がかかる。**そのため、実行ファイル名を `LinuxServer.x86_64` に固定することに決めた。** Unity側のビルド出力先は必ず `Versions/LinuxServer/LinuxServer` にすること(以後、これ以外の名前で出力しない)。

サーバー側のsystemdサービスファイルも、この固定名を指すように**一度だけ**更新しておく:

```bash
sudo tee /etc/systemd/system/nine-server.service > /dev/null << 'EOF'
[Unit]
Description=Nine Game Server
After=network.target

[Service]
Type=simple
User=toyama_family_from2006
WorkingDirectory=/home/toyama_family_from2006/game2
ExecStart=/home/toyama_family_from2006/game2/LinuxServer.x86_64 -batchmode -nographics -server
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
```

これを一度実行しておけば、以後は7.2の手順を毎回同じコマンドで実行するだけでよくなる。

### 7.3 サーバー基本情報

| 項目 | 値 |
|---|---|
| インスタンス名 | instance-20260806-055111 |
| ゾーン | us-west1-a（無料枠） |
| マシンタイプ | e2-micro |
| OS | Ubuntu 24.04 LTS |
| 開放ポート | 80/tcp, 443/tcp, 22/tcp（27777は外部非公開。Caddy経由でのみアクセス） |

### 7.4 Caddy設定（`/etc/caddy/Caddyfile`）

```
nine.freeddns.org {
    reverse_proxy 127.0.0.1:27777 {
        stream_timeout 1h
        stream_close_delay 30s
    }
}
```

設定変更後は `sudo systemctl reload caddy` で反映してください。

`stream_timeout` を明示的に長く設定しているのは、**ブラウザのタブが非アクティブになった際に生じる予期しない切断を防ぐため**です（Caddyのデフォルトタイムアウトのままだと、タブを長時間放置した際にWebSocket接続がCaddy側から強制的に切られることがあります）。

### 7.5 【重要】クライアントとサーバーの更新タイミングを必ず揃える

**WebGLクライアント（Cloudflare Pages）は`git push`のたびに自動デプロイされますが、Linuxサーバー（GCP VM）は自動デプロイされません。** サーバー側は手動でビルド→アップロード→再起動する必要があります（7.2参照）。

MirrorはクライアントとサーバーでC#スクリプト、特に`SyncVar`やCommand/RPCのシグネチャが完全に一致していることを前提に、ネットワーク上のデータをシリアライズ/デシリアライズします。**この前提が崩れると、コンパイルエラーやクラッシュにはならず、一見動いているように見えるのに挙動だけが不可解におかしくなる、という非常に気づきにくい不具合を起こします。**

実際に起きた例: `GameManager`に新しい`SyncVar`（`MaxPlayers`）を追加してWebGLクライアントだけを再ビルド・Pushしたところ、サーバー側は旧バージョンのままだったため、**「Join Roomを押した瞬間に一人でゲームが始まってしまう」**という、コード上はどこにも該当するロジックが存在しない不具合が発生した。原因はクライアント・サーバー間のバージョン不一致によるネットワークデータの解釈のズレだった。

**運用ルール**:
- `GameManager` / `Player` / `Room` / `RoomManager`など、`[SyncVar]`・`[Command]`・`[ClientRpc]`が付いたクラスに変更を加えた場合、**WebGLクライアントとLinuxサーバーの両方を同じタイミングでビルド・デプロイする**こと。片方だけ更新して様子を見る、ということはしない。
- サーバーだけ・クライアントだけを更新した状態でしばらく運用してしまった場合、原因不明のバグが起きたら、まず**「クライアントとサーバーのビルドタイミングがズレていないか」**を最初に疑うこと。
- Linux Dedicated Serverのビルドが `BuildPipeline.BuildPlayer` 経由（スクリプト実行）で `Unable to find an Linux Sysroot` のようなツールチェインエラーになる場合でも、**Unity Editorから手動でビルドすると成功することがある**(ツールチェインの初回セットアップがEditor UI操作でしかトリガーされない場合がある模様)。自動化でエラーになった場合は、手動ビルドも試すこと。

### 7.6 systemdサービス定義（`/etc/systemd/system/nine-server.service`）

## 9. レスポンシブUIシステムの仕組み

このプロジェクトのUIは、**機種（スマホ/タブレット/PC）を判定するのではなく、実際の画面解像度から連続的にレイアウトを計算する**方式を採用しています。長い試行錯誤の末にたどり着いた設計なので、仕組みを理解した上で触ってください。

### 9.1 CanvasScalerの基本方針

`ResponsiveCanvasScaler.cs` が、`CanvasScaler.referenceResolution` を**常に実際の画面解像度そのもの**に設定します。

```csharp
scaler.referenceResolution = new Vector2(Screen.width, Screen.height);
scaler.matchWidthOrHeight = 0.5f;
```

これにより `scaleFactor` が常に1になり、Canvas上の座標＝実ピクセルという単純な関係になります。機種を推測する分岐が一切不要になり、PCのウィンドウリサイズにも自然に追従します。

**注意**: UnityのWebGLはデフォルトで `devicePixelRatio` に合わせて物理ピクセルで `Screen.width/height` を返します。つまりiPhoneのようなRetinaディスプレイでは、CSS論理ピクセル（例: 390×844）ではなく、その3倍程度の物理ピクセル（例: 1170×2532）が実際の値になります。テスト解像度を設定する際は、**必ず物理ピクセル値を使う**ようにしてください（Apple公式サイトなどに載っている「解像度」の数値がこれにあたります）。

### 9.2 縦持ち/横持ちでレイアウトそのものを切り替える

単純な拡大縮小ではなく、縦持ち（portrait）と横持ち（landscape）で**要素の配置自体**を切り替えます。

- 横持ち: ロビーのボタン類は横並び、ゲーム画面の「使用済みカード一覧」は左上
- 縦持ち: ロビーのボタン類は縦積み、ゲーム画面の各要素は上から順に積み重なる

### 9.3 「連鎖配置」の考え方

各UI要素の位置は、**独立した固定割合の式で計算するのではなく、「直前の要素の実際の下端」を基準に次の要素を配置する**方式にしています（`ApplyOthersLayout` メソッド内）。

```
StatusText (タイマーバーの下)
  ↓ 間隔を保証
OthersCardParent / OthersLabelsParent (使用済みカード一覧)
  ↓ 間隔を保証
RoundResultPanel (このターンの結果)
  ↓ 間隔を保証
MyCardParent (自分の手札)
```

これは開発中に「独立した固定割合の式だと、解像度によっては要素同士が重なる」という不具合を何度も繰り返した末の設計です。**新しい要素を追加する際は、必ずこの連鎖の中に組み込み、前後の要素との間隔を明示的に計算してください。** 独立した固定値で配置すると、高い確率で別の解像度で重なりが発生します。

### 9.4 カードスケールに関する重要な注意点（幅と高さの両方を考慮する）

`UIEventsManager.RefreshMyCardView()` のカード拡大率は、**画面の「幅」から計算**されます（1行に何枚並べられるか、という考え方のため）。しかし、横持ちで幅が非常に広い画面（例: 1920×1080）では、幅から計算したカードスケールが大きくなりすぎ、**高さ方向の制約と噛み合わなくなる**問題が発生しました。

対策として、`ResponsiveCanvasScaler.cs` 側でも同じ計算式でカードスケールを見積もり（`cardScaleEst`）、それに基づいて「アンカー位置から下方向にどれだけカードが広がるか」（`cardDownwardExtent`）を計算し、画面外にはみ出さないための最低限のクリアランスを確保しています。

**今後、カードや同種の可変サイズ要素を追加する場合は、幅だけでなく高さの制約も必ず考慮してください。** 幅だけで計算すると、横長画面で高さが窮屈になった際に要素が画面外にはみ出します。

### 9.5 上限値（キャップ）を設定する際の注意

開発初期、カードや文字サイズの上限値を「スマホでちょうど良い値」で固定してしまい、後にタブレットやPCで「画面が広いのに要素が小さいまま」という不具合が繰り返し発生しました。**上限値を設ける場合は、固定値ではなく画面サイズに対する割合ベースにするか、十分大きな値にしてください。**

### 9.6 DebugPanelの扱いについて

`DebugPanel`（画面下部の「Debug: ...」「Add Bot」等）は開発・テスト専用で、本番ビルドには含まれません（`#if UNITY_EDITOR || DEVELOPMENT_BUILD` でコンパイル時に除外）。そのため、このプロジェクトでは**DebugPanelと他要素の見た目上の重なりは許容**する方針にしています（ただし、ボタン自体が画面内に収まり、タップ・クリック可能であることは必須要件です）。

## 11. 既知の問題・注意点

### 11.0 【最重要】Linuxサーバーをビルドした後は、必ずEditorのビルドターゲットをPlayerに戻す

**Unity Hubの「Build Settings」でLinux Dedicated Serverをビルドすると、Editor自体のアクティブなビルドターゲット(サブターゲット)が「Dedicated Server」のままになる。** これを`Player`に戻し忘れると、次のような深刻な不具合を引き起こす。

**発生する不具合**:
- `Utils.IsHeadless()`(Mirror本体の関数)が`UNITY_SERVER`シンボル定義により無条件で`true`を返すようになる
- これにより、Mirror本体の`NetworkManager.Start()`に組み込まれている「ヘッドレス環境なら自動でサーバーを起動する」機能が、Editor上でも意図せず発動する
- Play Modeに入った瞬間、何もクリックしていないのに`NetworkServer.active`が`true`になる
- この状態で「Create Room」を押すと、コルーチンの`WaitUntil(() => NetworkClient.ready)`が正しく機能せず`CmdCreateRoom`が失敗する(`"...called on Manager without an active client"`エラー)
- Play Modeを一度終了して入り直しても、次に「Host」を押すと`"Server or Client already started"`エラーになる

**確認方法**:
```csharp
// Unity内で実行して確認できる
Mirror.Utils.IsHeadless(); // Playerサブターゲットなら false のはず
```

**直し方**:
```csharp
UnityEditor.EditorUserBuildSettings.standaloneBuildSubtarget = UnityEditor.StandaloneBuildSubtarget.Player;
```
または、`File > Build Settings`のPC/Mac/Linux Standaloneの項目で、Target欄を「Dedicated Server」から「Player(Windows/Mac/Linux)」に戻し、Switch Platformする。

**運用ルール**: Linuxサーバーをビルドした直後は、**必ずこの設定を確認・復元してからEditorでの通常のPlay Modeテストに戻ること。**

### 11.1 Unity EditorのPlay Mode停止後もポートが解放されないことがある

Mirror（正確にはUnity Editor自体）の既知の問題として、Play Modeを停止してもネットワークのリスニングソケットがOSレベルで解放されないことがあります。この状態になると、次にPlay Modeでホストしようとした際に `SocketException`（ポート使用中）が発生します。

**対処法**:
1. まずドメインリロード（スクリプトの再コンパイル）を試す
2. それでも直らない場合は、**Unity Editorそのものを再起動**する
3. 緊急時の回避策として、SimpleWebTransportのポート番号を一時的に変更してテストを続行することも可能（ただし本番設定・Caddy側の設定と合わせる必要があるため、テスト後は必ず元に戻すこと）

### 11.2 "Manager" は接続前は非アクティブ

`UIEventsManager` がアタッチされている「Manager」というGameObjectは、**接続が確立するまで非アクティブ**です。そのため、接続前のロビー画面（未接続時のUI）に関わる処理を `UIEventsManager` 側に書いても実行されません。

このプロジェクトでは、接続前から必要な処理（レスポンシブレイアウトなど）はすべて `myNetworkManager.cs`（常時アクティブ）または `ResponsiveCanvasScaler.cs`（Canvasにアタッチ、常時アクティブ）側に実装しています。**新しく「接続前から見える必要があるUI」を追加する場合は、必ずこの点を意識してください。**

### 11.3 SyncListの宣言について

MirrorのSyncListやSyncObjectは、フィールド初期化子として `readonly` で宣言し、`OnStartClient`/`OnStartServer` 内で再代入しないこと。再代入するとMirrorのweaverによる同期登録が壊れます。

### 11.4 `[Command]` メソッドの制約

- `bool` を返り値にできない
- シーンオブジェクト（プレイヤーが所有しないオブジェクト）へのCommandには `requiresAuthority = false` が必要
